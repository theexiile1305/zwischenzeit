# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A native SwiftUI client ("Zwischenzeit") for the existing TTools practice-management backend at `https://www.ttools.app`: an iOS/iPadOS appointment calendar plus a watchOS "next appointment" app and widget. German UI.

Standing decisions:
- **Own calendar.** The app shows the calendar of the signed-in employee. There is no employee switcher.
- **Read-only, with one exception.** The app never creates, edits or deletes backend data, except the treatment documentation text (`TToolsAPI.saveDocumentation`). The other non-GET calls are `rest/login`, `rest/mfa`, `rest/revalidate` and `rest/logout`. Do not add other write endpoints. The backend has no documentation endpoint, so the save resends the whole Termin (see "Backend contract").
- **Unofficial client.** The project is not affiliated with the TTools vendor. The contract (see "Backend contract") mirrors what the TTools web client sends. Only test with your own account; never probe the backend beyond what the app does. Keep that section current when the contract changes.

## Commands

The Xcode project is generated by XcodeGen from `project.yml`. The generated `Zwischenzeit.xcodeproj` is checked in. After editing `project.yml`, run `xcodegen generate` and commit both.

Signing and identifiers come from `Config/Base.xcconfig` (committed, neutral `com.example` prefix, no team), overridden by the git-ignored `Config/Local.xcconfig`. Bundle IDs, the App Group (`APP_GROUP_ID`) and the background-task ID derive from `BUNDLE_ID_PREFIX`; Swift reads them at runtime (`Bundle.main.bundleIdentifier`, `AppGroupID` Info.plist key). Never hard-code them.

# Package tests (Swift Testing; no simulator or backend needed)

swift test --package-path Packages/ZwischenzeitKit --filter LiveAPITests                     # one suite

# Apps (derived data goes to build/dd, which is git-ignored)
xcodebuild -project Zwischenzeit.xcodeproj -scheme Zwischenzeit \
  -destination 'platform=iOS Simulator,name=iPhone 18 Pro' -derivedDataPath build/dd build

  -derivedDataPath build/dd -allowProvisioningUpdates build

Linting: `swiftlint lint --strict` (config `.swiftlint.yml`; `print()` is banned, use OSLog), `ruff check scripts`, `shellcheck scripts/*.sh scripts/ci/*.sh`. CI (`.github/workflows/`) also runs tests with coverage and sanitizers, app builds, XcodeGen/token drift checks, CodeQL, Semgrep, mobsfscan, gitleaks, zizmor and Scorecard. Actions are pinned by SHA; downloaded tools are pinned by version and SHA-256. mobsfscan needs `semgrep` on PATH (else every check reports "missing"); accepted risks are listed in `.mobsf`, false positives get an inline `// mobsf-ignore: <rule>` with a reason.

Releases: bump `MARKETING_VERSION` in project.yml and `CHANGELOG.md`, merge, then push a signed tag `vX.Y.Z`; `.github/workflows/release.yml` checks both and publishes the GitHub Release (see `docs/RELEASING.md`). Info.plist versions come from `MARKETING_VERSION`/`CURRENT_PROJECT_VERSION`.

Launch arguments (Debug builds only, via `AppModel.launchArguments`), read in `App/iOS/AppModel.swift` and `App/iOS/ZwischenzeitApp.swift`:
- `-mockAPI`: use `MockTToolsAPI` instead of the live backend. `-fixedNow <ISO8601>` freezes the clock and implies `-mockAPI`.
- `-signedOut`: mock starts signed out.
- `-watchEnabled`: turn on watch sync.
- `-calendarMode agenda|day|week|month`, `-route settings|firstAppointment|documentation`: open a specific view, for screenshots. `documentation` opens the first appointment with the editor sheet up.
- `-skipNotificationPrompt`: watch app, for simulators where the system prompt can't be tapped.

## Architecture

**Layout:**
- Thin app targets in `App/{iOS,Watch,WatchWidgets}`.
- Everything else is the local SwiftPM package `Packages/ZwischenzeitKit`:
  - Swift 6 strict concurrency.
  - iOS 17 / watchOS 10 / macOS 14 (macOS only so `swift test` and the gallery run without a simulator).
  - No third-party dependencies, and keep it that way.
  - `SettingsFeature` (and so `DocumentationFeature`) must also build for watchOS; `CalendarFeature` and `AppointmentFeature` are iPhone/iPad only. Keep watch-unavailable views behind `#if !os(watchOS)` and check with `xcodebuild -scheme SettingsFeature -destination 'generic/platform=watchOS Simulator' build`.
- Previews use `PreviewProvider`, not `#Preview`: the macro plugin ships only with Xcode, and the package must also build with the command line tools.

**App shell** (`App/iOS/ZwischenzeitApp.swift`):
- iPhone: a `NavigationStack` that opens on the agenda ("Liste").
- iPad: a `NavigationSplitView` (Kalender, Einstellungen) that opens on the week.
- A privacy cover shows in the app switcher and while the screen is recorded or mirrored (`ScreenCaptureMonitor`). The app locks behind Face ID / the device passcode on a cold start with a stored session and after 5 minutes in the background; Settings warns when the device has no passcode.
- `AppDelegate` disables third-party keyboards. The first launch of a fresh install clears the Keychain.
- Security decisions and accepted risks (e.g. no certificate pinning) are in `docs/THREAT_MODEL.md`. Keep it current when changing anything security-relevant.

**The API boundary:**
- `Domain/TToolsAPI.swift` defines the `TToolsAPI` protocol, the domain models (`Appointment`, `AppointmentService`, `Employee`, …) and `APIError`.
- Screens and view models only see this protocol and these models.
- There are two implementations:
  - `MockAPI/MockTToolsAPI`: a deterministic fake seed, used for previews, tests and screenshots. Employee `e1` is "Anna Hartmann".
  - `LiveAPI/LiveTToolsAPI`: the real backend.
- `App/iOS/AppModel.swift` is the single place that picks one. It holds session state, the owner, the app lock and watch sync.
- **Owner:** `AppModel.owner` is the session's employee. `owner.id` drives the calendar, the detail screen and the watch sync.
- German user-facing error strings live in the `APIError.message` extension in `Domain/APIErrorMessage.swift`.

**LiveAPI internals:**
- `HTTPClient` (actor):
  - Bearer token; HTTP status → `APIError`.
  - The backend answers **403 with "Invalid credentials"** for a bad login.
  - On a 401: a single-flight `rest/revalidate` with the `Refresh-Token` header, then one retry.
- `SecureSession`: the only URLSession for the backend (ephemeral, no `URLCache`, no cookies, TLS ≥ 1.2) with `RedirectGuard` (https, same host only). Never use `URLSession.shared`. `HTTPClient` asserts an https base URL.
- `TokenStore`: Keychain storage. The session's employee comes from the JWT claim `mitarbeiter`.
- `DTOs/`: lenient `Decodable` mirrors of the backend JSON.
- `Mapping.swift`: all wire-format rules live here. Non-obvious ones:
  - All timestamps are `"yyyy-MM-dd HH:mm"` Europe/Berlin wall-clock strings, parsed with `PracticeCalendar`.
  - The **day comes from `datum`; only the clock time of `uhrzeit`/`von`/`bis` is meaningful** (their date part is a placeholder). Use `Mapping.clock(_:on:)`.
  - A Termin is a sequence of `leistungen` run back to back from the start. Each Leistung carries its own `dauer`, `mitarbeiter`, `raum` and `terminart`. The appointment's employees, duration and treatment types come from the Leistungen.
  - n/m is `rezeptIndex+1/rezeptCount`, falling back to `terminSerieIndex+1/terminSerieCount` (both 0-based).
  - No `kunde` means a Freitext blocker (its text is in `dokumentation.text`).
  - Cancelled: `abgesagtAm`, `abgesagtDurchMandantAm` or `wahrgenommen == false`. `wahrgenommen == true` → `.arrived`: reception ticks it at check-in, **before** the treatment, so it never means "done" (the old raw value `"done"` still decodes). `trash` rows are skipped.
  - Blocked time is absences (`rest/mitarbeiter/urlaub`) plus the gaps between the employee's `mitarbeiterTermine` working windows.
  - `rest/mitarbeiter/` (no id) returns the SPA's HTML; the employee list is `rest/Stammdaten/entities/Mitarbeiter`.
  - `rest/Termine/` needs its trailing slash, which `URL.appendingPathComponent` drops; `HTTPClient` puts it back. Keep that when touching URL building.
- `appointments(for:in:)` fetches `rest/Termine/?date=` once per day in parallel, keeps a 60 s per-day cache, and filters by employee.
- The `LiveAPI` OSLog category (subsystem = bundle ID) logs counts and decoding-error paths only.

**Backend contract** (base URL `https://www.ttools.app/ttools/`, JWT Bearer):

| what | endpoint |
| --- | --- |
| sign in | `POST rest/login {principal: "<Einrichtung>_<Benutzer>", password}`: 200 returns tokens, 202 means MFA (temporary Bearer) |
| MFA | `POST rest/mfa {code}`: 401 wrong code, 423 locked, 429 rate-limited |
| refresh | `POST rest/revalidate` with header `Refresh-Token`, once per 401 (single-flight), then one retry |
| sign out | `POST rest/logout`, then the Keychain is cleared |
| session | JWT claim `mitarbeiter` → `GET rest/mitarbeiter/{id}`; no linked Mitarbeiter → `.noLinkedEmployee` |
| employees | `GET rest/Stammdaten/entities/Mitarbeiter` (array), without `status == INAKTIV` |
| rooms, treatment types | `GET rest/Stammdaten/Raum`, `rest/Stammdaten/Terminart` → `{data, columns}`; optional (empty on failure); no colours, the category is guessed from the name |
| appointments | `GET rest/Termine/?date=yyyy-MM-dd` (trailing slash required) → `{termine, mitarbeiterTermine}` |
| absences | `GET rest/mitarbeiter/urlaub/{id}?datumVon=&datumBis=` |
| documentation (the one write) | `PUT rest/Termine` with the whole Termin, like the web client's appointment form. `saveDocumentation` fetches `rest/Termine/{id}` as raw JSON right before, refuses if `dokumentation.text` is no longer what the editor started from (`DocumentationConflict`), replaces only that text, and sends every other field back as read (`LiveTToolsAPI.documentationUpdate`, unit-tested). Freitext blockers are refused. Only this one Termin is written, even in a group. |
| detail | `GET rest/Termine/{id}` → `{termine: [one]}`, plus prescriptions from `GET rest/Kunden/uebersicht/{kundeId}` (`rezeptStatus` 0 open, 1 cancelled, 2–4 completed; total = Σ `heilmittelLeistung[].anzahl`) |

**Features:**
- `CalendarFeature`:
  - `CalendarScreen`: header ("Heute"/"Morgen"/weekday, date and week number; tap for a date picker), a week strip of day pills in agenda and day mode, and the content view for the current `CalendarMode` (`agenda`, `day`, `week`, `month`).
  - `CalendarModel`: loads appointments and blocked intervals. Agenda and day mode load the whole strip week, and `reloadIfNeeded()` skips the request when the new day is already loaded. Pull to refresh and the menu call `reload()`.
  - `AgendaBuilder` (pure, unit-tested) turns a day into rows (appointments, free gaps ≥ 10 min, pauses), a summary and the next-up treatment. Pauses are blocked bands inside the working window. The summary's pause is the first band, else the longest gap ≥ 30 min. `AgendaView` draws it: next-up card, summary, earlier appointments folded away.
  - `DayLayout` (pure, unit-tested): column/overlap layout for the time grid.
  - `TimeGridView` (day, week) and `MonthView` (iPhone: count + load bar per day; iPad: chips).
- Check-in: `Appointment.checkIn(now:)` (`Domain/Appointment+Helpers.swift`) derives `waiting` (arrived, from 15 min before start until the end), `arrived`, `overdue` (not in 5 min after start) or `none`. `DSCheckInBadge` shows it in the agenda rows and on the next-up card, which turns green while the next patient waits. A running slot shows only the quiet check. The summary bar counts "da". The watch gets `UpcomingItem.isCheckedIn`, as of the last sync. Display only: the app never sets it.
- `AppointmentFeature`: the detail screen. It has a time-first header and prescription progress with a first/last-session callout. The owner's own name is left off the services. The documentation section opens the editor.
- `DocumentationFeature`:
  - `DocumentationEditor` is a sheet with a context header, a `TextEditor` and a Textbausteine chip bar above the keyboard. Inserts go at the cursor on iOS 18+ and at the end on iOS 17, spaced by `SnippetInsertion`.
  - `DocumentationEditorModel` keeps the draft in memory only. Before writing it re-reads the detail and, if the text changed in TTools meanwhile, offers "Beide behalten" / "TTools-Stand nehmen" instead of overwriting.
  - `SnippetStore` keeps the user's Textbausteine (`TextSnippet`, placeholders `{datum}` and `{behandlung}`, no patient name) as JSON in Application Support. They are managed in Einstellungen → Textbausteine.
- `SettingsFeature`: watch settings, owner and account, sign-out.
- `DesignSystem`:
  - Token-driven (`DS.Color.*`, `DS.Space.*`, `DS.Layout.*`), generated from `design/tokens.json`. Components use tokens, never raw values.
  - Components: `DSButton`, `DSBanner`, `DSEmptyState`, `DSStatusPill`, `DSDayPill`, `DSBadge`, `DSCheckInBadge`, `DSProgressSegments`, `DSHatch`, `EventCard`, `MonthChip`. `DesignGalleryView` shows them all; add new components there.
  - Treatment colours come from `TreatmentCategory`, which `Mapping.category` guesses from the Terminart name.
- `Appointment` helpers in `Domain/Appointment+Helpers.swift`: `isFirstSession`, `isLastSession`, `sessionLabel`, `durationMinutes`. That file also holds `Countdown` (German "in 12 Min." texts, shared by phone and watch).

**Watch data path:** the watch never talks to the backend and holds no credentials.
1. On the iPhone, `AppModel.performWatchSync()` loads the owner's today and tomorrow.
2. `WatchSync/UpcomingBuilder` formats them per the user's privacy settings (`WatchSettings`: name display, treatment, room, lead time). The session label (n/m) is always sent; it contains no name.
3. `PhoneWatchBridge` sends the result via `WCSession.updateApplicationContext`.
4. On the watch, `WatchReceiver` stores it as JSON in the App Group (`APP_GROUP_ID`, read from the `AppGroupID` Info.plist key).
5. The watch app, the widget (`App/WatchWidgets`) and the local notification scheduling read that file. Notifications are local only (no APNs, no tokens). `NotificationContent` builds the text; the long look (`NotificationController`, `WKNotificationScene`) renders `WatchNextCard` for the id in `userInfo`.

Sync runs on launch, on foreground, after calendar loads, after settings changes, and from a background task (`<bundle ID>.watchsync`).

Phone and watch can run different app versions. New fields on `UpcomingItem`/`UpcomingPayload` must decode as optional or with a default (see its `init(from:)`), and need a test with an older payload.

## Data handling

This app shows real patient data:
- Test fixtures in `Tests/LiveAPITests/Fixtures` are synthetic data in the real payload shape. Never commit real names, notes or tokens.
- Logs must stay free of names, free text and tokens.
- Patient text on the watch (app and widget) is `.privacySensitive()`, so it is redacted on a locked watch and the always-on face.
- There is no on-device persistence of appointments beyond the watch payload. Documentation drafts stay in memory. Textbausteine are stored on the device and must not contain patient data.
